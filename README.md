# Book recsys pipeline (PySpark)

Проект построения ETL для рекомендаций книг/аудио.

Этапы работы:
    1. Загрузка данных из S3
    2. Очистка данных
    3. Join данных
    4. Построение 5 витрин
    5. Сохранение данных в Parquet

## Инструкция по запуску

Запуск спарк приложения осуществляется через sh-файлы обертки. Они запускают main.py с различными параметрами (параметры можно передавать в sh-файл, они будут проброшены в main.py, например `./submit.sh --show-plan`).

```bash
./start.sh - стартует spark в докере локально.
./submit.sh - запускает spark-submit и передает параметры (зашиты в скрипт)
./stop.sh - останавливает spark в докере (локально)

./server_submit.sh - запускает spark-submit на сервере (YARN), необходимо запускать из серверной консоли
```

## Оптимизация под YARN

На Jupyter/YARN driver живёт в client mode на поде с лимитом RAM. Симптом OOM — `Killed` без stack trace, всегда воспроизводился на записи `user_mart`.

Что помогло прогнать все 5 витрин:
- `spark.sql.autoBroadcastJoinThreshold=-1` — без broadcast join, таблица `content` не держится на driver.
- `spark.driver.memory=4g` в `server_submit.sh` (8g только увеличивало шанс OOM-killer на поде), но не проверено откат на 8g.
- В `make_marts` первые три витрины пишутся в S3 до построения `content_mart` / `daily_user_mart`.
- На сервере без `--verbose` (лишние count/show до витрин).


### Параметры скрипта main.py (редактируется в sh)

- `--show-plan` - выводит план выполнения запроса построения витрины user_mart.
- `--verbose` - show/count для отладки и примеров в README; на сервере не нужен.
- `--columns usage_platform_ru main_content_type genre` - распределение по уникальным пользователям в разрезе указанных столбцов (genre — через explode).
- `--show-analytics` - аналитика hours по дням недели и geo.

## Наблюдения

- Загружены данные из S3.
    - В таблице прослушиваний (`audition`) примерно 1М строк и 12 столбцов.
    - В таблице контента (`content`) примерно 32к строк и 6 столбцов.

### Задача 2. Первичный анализ данных

- Описание столбцов `audition`:
    - audition_id - уникальный идентификатор сессии чтения или прослушивания.

### Задача 3: предобработка и анализ данных

- Предобработка данных:
    - Преобразование столбца msk_business_dt_str в тип date (timestamp не требуется, так как данные хрятят только дату без времени)
    - Преобразование столбца published_topic_title_list в тип список строк.

- Очистка данных:
    - Перед чисткой считаем пропуски и кривую длительность в обеих таблицах.
    - app_version в audition пустой в ~702k строк (70%) - заменили на unknown.
    - hours/hours_sessions_long вне диапазона 0..24 - удалили 56 строк из audition.
    - В таблице content до очистки (логируется всегда): 6 пропусков в main_content_duration_hours, 1 строка с длительностью <= 0 (ноль), отрицательных нет. В clean_content null и <= 0 заменяем медианой по строкам с duration > 0 — всего 7 строк.

До джойна двух таблиц произведена фильтрация по датам и гео. Параметры фильтрации берутся из опций скрипта.

- Join audition и content по main_content_id - inner. На полной выгрузке после очистки: 1 002 840 сессий до join, 996 509 после. Выпало 6331 (~0,6%) - у этих сессий id контента нет в каталоге content. Оставлять их с пустыми полями смысла нет: без названия, жанров и длительности книги витрины и finished_percent не посчитать, поэтому режем join-ом, а не fillna.

### Задача 5. План выполнения user_mart

План снят через `explain(mode="extended")` на user_mart, сохранен с сервера в `server_exec_plan.md`. Анализ по блоку `Physical Plan`.

Перемешивание. Shuffle в плане - это узлы `Exchange hashpartitioning`. Их достаточно много (27 шт): перед каждой группировкой по пользователю, перед join, перед window с `row_number` (топ жанра, платформа, тип контента), плюс шаффл на join audition/content в каждой ветке. Отдельно шаффл в ветке favorite_genre - там join идет сразу по двум полям (puid и main_content_id), не только по puid. Шаффлы - тяжелые операции, требующие перераспределения данных между экзекуторами.

Типы join. Audition с content Spark джойнит через SortMergeJoin (broadcast отключён в конфиге из-за OOM-ошибки) - в каждой из веток метрик свой join + sort/exchange по main_content_id. Сам user_mart собирается цепочкой SortMergeJoin LeftOuter по puid - их пять штук подряд в верхней части плана. Еще один SortMergeJoin Inner - внутри расчета favorite_genre, после explode жанров.

Что дороже. Самое заметное - FileScan на audition.parquet встречается в плане 7 раз. Каждая метрика user_mart тянет свою ветку с нуля. Тяжелая ветка - favorite_genre: explode, join по двум ключам, window. Пять SortMergeJoin на финале выглядят лишними - справа уже агрегаты по puid, таблицы небольшие. Из плюсов: фильтр по hours (0..24) уже уходит в чтение parquet (PushedFilters), базовые метрики вроде total_hours Spark считает за один проход (в плане видно Expand перед agg).

Что можно улучшить (в коде не реализовано).
- Закешировать joined после очистки - тогда не придется столько раз читать один и тот же parquet. Наверно это одно из главных моментов, которые можно улучшить.
- Собирать user_mart из уже готовых user_content_mart и user_genre_mart: completion_rate и favorite_genre в плане пересчитываются из joined, хотя эти витрины строятся раньше.
- unique_genres_count логичнее брать из user_genre_mart, а не раскрывать жанры еще раз.
